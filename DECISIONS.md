# DECISIONS.md — judgment calls made while building the GasSetu prototype

Each entry: what the PRD said (or didn't), what was chosen, why.

## Private business documents (22 Oct 2026)
- **Object bytes stay outside PostgreSQL and behind the API.** PostgreSQL stores immutable content metadata, versions, ownership, retention class, archive/legal-hold state, and an append-only access ledger. Download and preview stream through permission checks; browsers never receive unrestricted object-storage credentials or public bucket URLs.
- **The adapter is provider-neutral and fail-closed.** Local private storage exists only for development/test. DigitalOcean Spaces uses the S3-compatible adapter when credentials are connected. Production defaults to `disabled`, and local storage is configuration-invalid outside local/test.
- **Uploads require two independent enables.** The Super Admin `features.document_uploads` control and a live object-storage provider must both be enabled. This prevents a configuration toggle from silently writing to an unapproved or unavailable service.
- **Uploaded content is bounded and verified.** Only PDF, JPEG, PNG, and WebP are accepted, at a maximum of 10 MiB. The API checks file signatures, stores a SHA-256 digest, re-verifies size and digest before access, and quarantines mismatches.
- **Archive is retention, not deletion.** Archiving requires fresh MFA and a reason, leaves the private object intact, and appends both document and platform audit events. Physical deletion and class-specific retention expiry remain disabled until legal policy and a tested backup/recovery process are approved.
- **Spaces remains a connection checkpoint.** It is outside the current USD 45 ceiling, so no bucket or credential is provisioned by this workstream. Production upload activation waits for separate budget approval, a private-bucket smoke test, credential-scope review, and independent object recovery testing.

## Super Admin execution controls (21 Oct 2026)
- **Configuration is a closed, versioned catalogue.** Super Admin can govern six transaction workflows, two operational thresholds, and two infrastructure-dependent feature gates. Unknown keys and invalid types/ranges are rejected; optimistic versions prevent one administrator from silently overwriting another.
- **Workflow gates are enforced by APIs.** Tenant onboarding, ordering, COD, credit, agency fulfilment, collection recording, and push registration consult PostgreSQL before executing. The dashboard is an operating surface, not the security boundary.
- **Every configuration change requires fresh MFA, a reason, and before/after audit values.** Ordinary Platform Admin roles cannot obtain reserved `configuration.manage` authority through delegation ceilings.
- **Infrastructure-dependent features default off.** Push registration and document uploads remain disabled until their production services are connected and acceptance-tested. Disabling push registration never prevents a user from revoking an existing device.
- **Internal audit routing is explicit configuration.** `INTERNAL_AUDIT_MODE=true` preserves fictional read-only client review entry points; setting it to `false` restores authenticated `/control` and `/operations` dashboards without deleting the review pages.

## Production Operations command centre (21 Oct 2026)
- **Agency reporting is transactional and scope-bound.** `/operations/dashboard` reads orders, fulfilment transitions, inventory, commercial accounts, invoices, collections, and named delivery capacity directly through the protected API. Every request requires `agency.view` inside the selected agency scope; no cross-agency aggregate or mock fallback exists.
- **Operational periods use Asia/Kolkata.** Daily, weekly, and monthly comparisons share the Platform Control reporting timezone. Booked value is labelled separately from delivered value, collections, settlement, and revenue so the dashboard does not imply unsupported accounting equivalence.
- **Exceptions stay actionable and factual.** The command centre identifies failed deliveries, delayed acceptance/assignment, low stock, and overdue accounts from persisted state. It does not invent targets, forecasts, staffing recommendations, or estimated service outcomes.
- **Dashboard scans receive a dedicated access path.** Migration `0012_operations_dashboard` adds `(agency_id, created_at desc, id desc)` because the older status-leading index cannot efficiently serve all-status reporting windows.

## DigitalOcean in-place production promotion (16 Oct 2026)
- **The existing paid environment is production.** The DigitalOcean project environment, App Platform app name, and API/web `APP_ENV` values were changed from staging to production in place. This preserves the tested app, firewall attachment, database, stable provider hostname, and USD 45 monthly ceiling instead of paying for a duplicate environment.
- **Legacy database identifiers remain labels only.** The managed cluster and database keep their existing `commercial-lpg-staging-db` and `platform_staging` identifiers to avoid a risky data move. Runtime behavior is controlled by `APP_ENV=production`; future infrastructure uses the production-named template.
- **Automatic deployment stays off.** Production releases remain deliberate until real SMS delivery, authorization acceptance testing, and operational monitoring are complete.

## Mobile notifications and OTA boundary (16 Oct 2026)
- **Expo Go is the immediate review surface, not the remote-push acceptance surface.** It supports the current UI and local notifications, while a signed development/preview build is required to validate remote push and EAS Update behavior.
- **Push registrations are tenant-authenticated and installation-unique.** Expo tokens are encrypted with a dedicated production key, never logged or returned, and atomically reassigned on an account switch so a physical installation cannot keep receiving notifications for a previous user. Logout independently attempts push-token and session revocation.
- **Push delivery reuses the transactional outbox.** Order, invoice, and payment events fan out only to active devices owned by active members of the affected active tenant. Each event/device result is idempotent and inspectable, transient failures have a bounded retry ceiling, and an Expo `DeviceNotRegistered` result makes the installation stale.
- **The production worker can be push-only.** `MESSAGE_PROVIDER=disabled` keeps incomplete SMS delivery fail-closed while `PUSH_PROVIDER=expo` processes commercial notifications. The same worker will add MessageIndia later rather than introducing a second paid component.
- **The final commercial identity precedes EAS project creation.** The working GasSetu label and `com.gassetu.demo` identifiers remain review-only. A permanent Expo project, bundle IDs, Apple/FCM credentials, and production OTA publishing wait for the approved final name and ownership account.

## Production Phase 1 commercial-account and tenant self-service slice (16 Oct 2026)
- **Agency controls stop at the commercial boundary.** Agency users may globally pause new credit ordering, maintain lower negotiated account prices, and record collections. Credit approval, account limits, and net terms remain platform-admin decisions and have separate permissions and endpoints.
- **Collection history is an append-only ledger.** Each payment is recorded once, idempotently allocated to the oldest outstanding invoices, protected by cross-account database guards, and rejected if it exceeds current receivables. Advance balances require a later explicit model rather than an implicit negative invoice balance.
- **Suspension does not obstruct debt collection.** A suspended commercial account cannot receive pricing changes or new orders, but an authorized agency can still record settlement against its existing invoices. Closed accounts reject further collection activity.
- **Tenant self-service is strictly tenant-scoped.** Order history, timelines, billing summaries, invoice details, and payment allocations require an active membership, active tenant, active agency assignment, approved agency, and open commercial account. Pagination uses opaque keyset cursors.
- **Tenant lifecycle and credit state are separate controls.** Suspending a tenant revokes live sessions and blocks tenant access. Reinstating the tenant does not implicitly approve or reinstate credit; credit exposure is checked before reducing a limit or suspending an account.
- **Agency-wide credit is an availability switch, not a terms mutation.** Disabling it blocks new agency credit orders and approvals without rewriting platform-owned per-account limits, net terms, or historical invoices.
- **Database design follows production PostgreSQL safeguards.** Foreign-key access paths are indexed, payment writes use short ordered row-lock transactions, monetary values are exact numerics, and hot lists use composite keyset pagination rather than offsets.

## DigitalOcean staging deployment slice (30 Sep 2026; deployed 9 Oct 2026)
- **Staging has a USD 45 all-in monthly authorization ceiling.** The deployed footprint uses a 512 MiB API, fixed 1 GiB dashboard, short-lived 512 MiB migration job, and single-node 1 GiB PostgreSQL. The ordinary recurring estimate is USD 35.58 including 18% GST; the conservative provider proposal, including the job's nominal monthly rate, is about USD 41.48. Adding even the smallest worker would raise that conservative proposal above the ceiling, so the worker, Spaces, HA, dedicated compute/IPs, extra database nodes, and autoscaling remain gated on optimization or separate approval.
- **One App Platform app fronts the dashboard and API.** The Next.js dashboard owns `/`, while ingress preserves `/v1` for the API. Dashboard server calls use App Platform's private `http://api` service route, and mobile clients use the public `/v1` route on the provider-generated domain.
- **Managed PostgreSQL is attached, not synthesized by application code.** The spec binds an existing PostgreSQL 16 cluster by confirmed cluster, database, and user names. Separate App Platform bindings supply the runtime and migration identities. In staging, both use the managed public TLS endpoint with CA-verified hostname checks because the private endpoint was unreachable from the app; the database firewall trusts only this App Platform app.
- **Migrations are a pre-deploy release gate.** A single-instance `PRE_DEPLOY` job runs the forward-only migrator under its advisory lock before new API/web containers receive traffic. Runtime services never receive the migration-owner credential.
- **The staging spec is rendered, not committed with secrets.** Repository/database identifiers and first-submission secrets remain unresolved in the tracked template. A validating renderer writes mode-`0600` `.do/app.yaml`, which is git-ignored. After first submission, the plaintext rendering is replaced by DigitalOcean's canonical encrypted spec and temporary local credential exports are removed.
- **The messaging worker remains gated on a real provider.** The worker correctly refuses the local adapter in staging/production. Omitting it from the first infrastructure-health deployment is safer than weakening that guard; it is added only when the SMS provider adapter and credentials are available.
- **Automatic deployment starts disabled.** The first releases remain operator-triggered until migration, restore, authorization, and provider-delivery smoke tests pass in staging. The undecided product name and domain do not block the provider-generated staging URL.
- **Recovery drills use isolated targets and matching PostgreSQL tooling.** The first database drill restored a PostgreSQL 16 logical backup into a temporary same-cluster database, compared schema inventory, columns, and data, reran migrations and all verification suites, then removed the database and temporary firewall access. The first App Platform drill deployed current `main`, rolled back to the known-good release, and rechecked all public routes. A full managed-backup restore remains separate because DigitalOcean creates a new billed primary cluster for that operation.

## Production Phase 1 Platform Control slice (30 Sep 2026)
- **Production administration is isolated at `/control`.** The existing `/admin` remains an investor-demo surface. Platform Control uses only the protected PostgreSQL API through the HttpOnly same-origin gateway and never imports mock personas or the demo engine.
- **Read authorization is applied in SQL.** Tenant queues, agencies, summaries, receivables, roles, and team rosters are constrained by active permission assignments before rows or aggregates leave PostgreSQL. Global, state/region, city, agency, selected-agency, and tenant scopes are represented; the browser is not a security filter.
- **Analytics have explicit boundaries.** Super Admin sees platform-wide figures through global scope. Platform Admin/team see the same metric definitions only for their assigned scope. Tenant analytics remain in the tenant API and agency fulfillment metrics remain in agency operations. Platform Control returns onboarding progress, order value/counts, deliveries, credit decisions, and receivables—not tenant consumption secrets or another agency's operations.
- **Operational periods use Asia/Kolkata.** Daily, weekly, and monthly dashboard boundaries are calculated server-side in the confirmed business timezone while timestamps remain stored as `timestamptz`.
- **Onboarding remains maker–checker.** Team members create and submit a complete draft with mandatory GSTIN, owner, outlet, requirement, and explicitly selected agency. A distinct authorized reviewer approves, requests changes, or rejects. Credit approval is a separate permission and decision inside activation; deferred or rejected credit activates prepaid access.
- **Delegation remains below the actor ceiling.** Platform Admins can create only roles using permissions they hold, ordinary team roles cannot receive reserved permissions, and team identities receive MFA-required SMS invitations with explicit global/city/agency scope.
- **Lists use keyset pagination and indexed read paths.** Tenant pages use `(created_at, public_id)` cursors rather than OFFSET. Dedicated indexes support status queues, time-bounded order summaries, scoped receivables, active role assignments, and approved-agency selection.
- **Privileged login is phone OTP plus provider-neutral TOTP.** Phone verification issues only a short-lived, single-use, HMAC-hashed MFA ticket. First login enrolls one encrypted authenticator factor and reveals ten individually hashed recovery codes once; later login accepts a fresh TOTP step or consumes one recovery code. Successful MFA alone issues an `otp_mfa` session, while replayed TOTP steps and exhausted tickets fail closed.

## Production Phase 1 agency fulfillment slice (30 Sep 2026)
- **Agency operations use a separate production surface.** `/operations` does not import the investor-demo engine or its seeded personas. It authenticates against the production API and shows only agencies covered by the user's active RBAC assignments.
- **The browser never receives the bearer token.** The Next.js same-origin gateway exchanges OTP verification for a secure, HttpOnly, SameSite session cookie, allowlists the small operations API surface, forwards mutations only from the same origin, and keeps the upstream API URL server-only.
- **Stock is reserved when the agency accepts.** Acceptance atomically checks and reserves full cylinders; dispatch deducts both physical and reserved stock. Rejection and cancellation are constrained by order state, while failed delivery returns dispatched stock before a reschedule can reserve it again.
- **Inventory movement is an append-only ledger.** Every reservation, release, dispatch, return, delivery, and empty receipt records deltas plus post-movement balances. Database triggers reject update or deletion of ledger entries.
- **Order transitions are permissioned and idempotent.** View, edit, and execution permissions are distinct and agency-scoped. Each transition uses a request hash and retained browser retry key, row-locks the order and inventory in stable order, writes the status history, audit event, and outbox message in one short transaction, and returns the original response for an identical retry.
- **Delivery is the invoice boundary.** COD requires cash confirmation and produces a paid invoice. Approved-credit delivery produces an open invoice using the admin-owned net term. Collected empties update agency and outlet custody counts; unreturned cylinders increase the agency's `with_accounts` balance.
- **First operations UI is deliberately a control console.** It covers queue review, accept/reject/cancel, staff assignment, dispatch, failed-delivery recovery, empty-cylinder capture, COD confirmation, invoice result, and current stock. Driver login, delivery OTP, route tracking, collections, and replenishment adjustments remain later production slices rather than being inferred from the demo.

## Production Phase 1 tenant ordering slice (30 Sep 2026)
- **The server owns every commercial total.** The mobile app submits cylinder codes and quantities only. The API resolves active agency prices, the best applicable quantity slab, and a lower account-negotiated price; then calculates delivery charges and 18% GST using integer paise before persisting exact PostgreSQL numeric values.
- **A quotation is an expiring database snapshot, not client state.** Quotes bind the tenant, outlet, agency, commercial account, user, slot, payment method, item prices, taxes, and total for ten minutes. Order placement recomputes current prices and policy and rejects a stale or changed quote rather than trusting displayed totals.
- **First production payment modes are COD and approved credit.** COD follows the agency global switch. Credit requires an open account, an approved admin-owned limit and net term, agency-wide credit availability, no overdue invoice, and enough available exposure. UPI/card/netbanking remain fail-closed until the payment adapter, server order creation, signature verification, and webhooks exist.
- **Credit checks serialize on the commercial account.** Order placement locks the account (and its credit record when present), recalculates pending-order and invoice exposure, then creates the order in the same short transaction. Concurrent devices therefore cannot independently consume the same remaining limit.
- **Order creation is idempotent and auditable.** A scoped idempotency key returns the exact original response for an identical retry and rejects reuse for another body. The order, line snapshots, initial status event, quote consumption, transactional outbox event, and immutable audit event commit together.
- **Tenant analytics remain bounded to tenant data.** The first tenant home response exposes only its own business identity, outlets and stock counts, assigned agency, price catalogue, permitted delivery slots, payment eligibility, and its own credit limit/exposure. Platform or other-tenant operational data never enters this contract.

## Production Phase 1 protected onboarding slice (30 Sep 2026)
- **One-time Super Admin bootstrap is explicit and audited.** A database-owner command creates or reuses one named person, a reserved global Super Admin role, and the full current permission catalogue. It is idempotent, refuses a second Super Admin unless explicitly authorized, requires a reason, and never creates a login session or shared password.
- **Production sessions are opaque and revocable.** The API stores only an HMAC-SHA-256 token digest, accepts active unexpired sessions for active users, periodically touches `last_seen_at`, and requires an MFA-verified session whenever the user is marked `mfa_required`.
- **Authorization is default-deny and scope-aware.** Every protected mutation must match both a permission and an active assignment scope. Global, region, city, agency, selected-agency, and tenant scopes are represented server-side; city comparisons are normalized case-insensitively.
- **The first protected mutation creates a tenant draft only.** `POST /v1/admin/tenants` atomically creates or safely reuses the owner identity, tenant, owner membership, initial outlet, structured requirement, proposed serving-agency assignment, commercial proposal, idempotency result, and immutable audit event. It cannot activate the tenant or send an invitation.
- **Credit entered during creation is a proposal.** A requested limit and net-7/15/30 term is stored as pending; it does not create an approved credit account. Prepaid requires no credit decision. Approval remains a separate Platform Admin operation.
- **GSTIN receives local structural/checksum validation.** This catches input errors before persistence. Authoritative taxpayer-status verification remains an external integration at approval time and must not be inferred from a locally valid checksum.
- **Invitation delivery remains approval-gated.** No SMS or WhatsApp event is created by draft creation. The later approval transaction will activate the tenant and enqueue SMS-first delivery, with WhatsApp only after the approved fallback policy.
- **Role delegation enforces both ceiling and scope.** Custom roles cannot contain permissions the creator lacks; ordinary platform-team roles cannot receive reserved approval powers. Role assignment separately checks that the administrator controls the target global/region/city/agency/tenant scope.
- **Privileged team identities are invitation-gated.** Assigning a role creates an MFA-required invited identity and a transactional SMS-first access-invitation event. The active role assignment alone cannot create a usable session while the identity remains invited.
- **Submission and review are separate transitions.** Creators can idempotently submit a draft into `pending_approval`; a reviewer with scoped permission can request changes, reject, or approve. Approval activates the tenant and proposed agency assignment in the same transaction.
- **Activation and its side effects are atomic.** Commercial account creation, optional credit-account approval, tenant invitation, outbox event, review, and immutable audit event commit together. A database trigger independently blocks invitations for non-active tenants.
- **Deferred credit does not block onboarding.** A requested credit decision can be deferred while the tenant activates with a prepaid account. Only an authorized credit approver can approve or reject the request, and agency-level credit disablement blocks approval.
- **Messaging is provider-neutral and fail-closed.** The worker depends on a small channel/template/idempotency contract rather than a vendor SDK. The deterministic local adapter is permitted only in local/test; staging and production refuse to start it until a real provider adapter is selected.
- **OTP plaintext is not persisted.** Verification uses a dedicated HMAC pepper. Worker delivery uses a separate AES-256-GCM key and challenge-bound associated data, so the outbox contains only an authenticated ciphertext envelope.
- **OTP request responses resist account discovery.** Unknown, ineligible, cooldown, and rate-limited numbers receive the same accepted response shape. Phone/IP limits store keyed hashes rather than raw rate keys; active codes are single-use with bounded attempts and resend windows.
- **Tenant OTP and privileged access diverge intentionally.** Successful tenant OTP activates invited memberships and creates an opaque revocable session. Phone verification for an MFA-required platform identity activates the identity but returns an MFA handoff; no privileged session exists until authenticator or recovery-code verification succeeds.
- **Production mobile authentication is isolated from the demo engine.** Tenant OTP calls use the platform API without offline/demo fallback, opaque tokens use the native device secure store, launch restoration revalidates the server session, logout revokes it, and multi-tenant identities explicitly select an active business. Prototype personas require an explicit demo build flag.

## Production Phase 1 foundation (29 Sep 2026)
- **Production runtime is isolated from the demo engine.** `apps/api` and `apps/worker` are new production processes. `apps/mock-api` remains demo-only and is not a deployment target for tenant data.
- **PostgreSQL is accessed through bounded pools.** API and worker pools have explicit connection, statement, idle, and idle-in-transaction timeouts. Production database TLS requires CA-verified `verify-full` mode.
- **The API starts closed.** The initial public surface contains liveness, database-backed readiness, and a version marker only. Tenant mutations are not exposed until production authentication and server-side authorization are implemented.
- **Background work uses the transactional outbox.** Workers claim only registered event types through `FOR UPDATE SKIP LOCKED`, perform external work outside the claiming transaction, and release failures with capped exponential retry. With no provider handlers registered, the worker leaves events untouched.
- **Deploy compiled artifacts on Node.js 22.** API and worker TypeScript is bundled into small ESM artifacts while the PostgreSQL driver remains an external runtime dependency. The root engine is pinned to DigitalOcean's supported Node.js 22 line.
- **Dashboard builds are network-independent.** Build-time Google Font fetching was removed in favor of the established system font stack. Next.js production builds use its supported webpack mode because the current Turbopack CSS worker cannot bind its internal port in restricted build environments.

## Production Phase 0 (29 Sep 2026)
- **Phase 0 approved and closed.** `PRD_PRODUCTION_V1.md` version 1.0 is the locked product baseline for Phase 1 architecture and implementation.
- **DigitalOcean is the production cloud baseline.** Phase 1 will target DigitalOcean App Platform for the web/API/worker workloads, Managed PostgreSQL for transactional data, a private VPC for service-to-database traffic, and private Spaces object storage for business documents. Bangalore (`blr1`; App Platform region `blr`) is the confirmed primary region. The commercial product name and custom domain are intentionally deferred; GasSetu remains a working name and must not become a deployment dependency.
- **Team-led tenant creation replaces self-registration.** An authorized platform team member registers the business, mandatory GSTIN, initial outlet, LPG requirement, user phone, serving agency, and proposed commercial terms. A Platform Admin activates the tenant; an unknown phone cannot create an account from the app.
- **Maker–checker approval is mandatory.** Ordinary team members cannot approve tenants or credit. The tenant creator cannot approve their own submission. A Platform Admin approves team submissions; a Platform Admin's own submission requires another Platform Admin or a Super Admin override. Invitation delivery starts only after approval.
- **Agency selection is explicit.** The authorized creator must select an approved serving agency. Production onboarding does not use nearest-agency auto-assignment.
- **Invitation delivery is SMS-first with WhatsApp fallback.** WhatsApp is attempted only after SMS fails or remains undelivered beyond the configured fallback window. Provider attempts and callbacks are auditable and idempotent.
- **OTP login starts after approval.** Once a Platform Admin approves the submission, the tenant is activated and invited. The registered tenant can then use the mobile app; first login shows the registered account rather than another onboarding wizard.
- **Credit authority stays with platform admin.** Only platform admins approve credit and manage limits/net terms. Agencies can record payments, manage negotiated pricing, and disable credit globally for their own operation.
- **Super Admin and delegated RBAC.** A Super Admin sits above Platform Admins with global executive, configuration, audit, override, and reporting authority. Platform Admins add their teams and delegate resource/action/scope permissions only within their own permission ceiling.
- **Analytics is bounded by role and scope.** Super Admin receives platform-wide executive and operational reporting; Platform Admin/team receives scoped operational reporting; tenants see only their own outlets, operations, spend, billing, credit, and service performance.
- **Approved implementation defaults.** A phone identity may belong to multiple tenants; Platform Admin/team access is scoped by city/region and optionally agencies; multiple named Super Admin accounts are supported; GSTIN receives format/checksum validation and authoritative verification before approval when integrated; WhatsApp fallback starts after a configurable five-minute SMS window; tenant-controlled fields are limited; admin pricing overrides are separately permissioned and audited; v1 credit terms are net-7/15/30 with Super Admin override for exceptions.
- **Active product language is B2B-only.** Restaurants and hotels are the primary tenant segments. Domestic/refill-era material is historical and remains available at the `b2c-prototype` tag.
- **Production source of truth:** `PRD_PRODUCTION_V1.md` supersedes earlier documents where onboarding, authentication, agency assignment, tenant verification, permissions, or credit ownership conflict.

## Approved deviations (plan step, 16 Sep 2026)
1. **`packages/engine` instead of a second bundled mock store.** All business logic (store, state machine, rules, route simulation, demo controls) lives in one pure in-memory `DemoEngine`. `apps/mock-api` wraps it over HTTP + WebSocket; the mobile app instantiates the same engine locally if the API is unreachable. The route table (`packages/engine/src/routes.ts`) is framework-independent so the offline fallback serves the *exact* same endpoints. Offline fallback is mobile-only — the web panel's purpose is live multi-client data.
2. **No NativeWind.** Plain `StyleSheet` + `@gassetu/ui-tokens`. Fewer Babel/Metro moving parts for a stage demo.
3. **Maps:** `react-native-maps` on iOS/Android (Apple Maps on iOS Simulator, no key); platform-split SVG map card on web (`*.web.tsx`).
4. **Tracking simulation runs on the server.** "Start trip" starts route playback in the engine, which broadcasts `staff.location` every 1.5 s (scaled by demo speed). Customer and agency maps move even if the delivery screen is closed.
5. **No timers for reject/timeout.** Rejection is manual only.
6. **Relative seed dates.** History is generated relative to the run date with a fixed faker seed (names/addresses stable, charts always "last 90 days").

## Seed data
- **~100 customers (75 domestic / 25 commercial) instead of 40** so that realistic ordering frequency (domestic ≈ monthly, commercial 2–3×/week) yields ~970 bookings over 90 days and the agency's daily chart isn't dwarfed by the 14 "live" orders seeded for today. (With 40 customers the history came out at ~350 bookings / ~3 per day for Suresh.) 57 % of customers belong to Suresh's agency.
- Riya's history: four 14.2 kg deliveries exactly 30 days apart, last one 26 days ago → gauge shows **~13 % left, refill in ~4 days** (PRD script says "~15 %, 3 days" — same story, computed rather than hard-coded).
- `reminderLeadDays = 2` so that a delivery today schedules the reminder 28 days out (PRD script: "14 Oct" for a 16 Sep delivery).
- Historical `DELIVERY_FAILED` orders older than a day are auto-cancelled in the seed so they don't linger as open orders on the board; one live failed order from today remains for the demo.
- Gachibowli agency has COD disabled (to demo the "COD not available" path). Suresh's agency has 5 kg FTL stock below threshold (low-stock alert visible on first load).
- GST (5 %) is applied only to delivery + fees, not to the cylinder price (domestic LPG has its own tax treatment; this is illustrative).

## Engine behaviour
- `booking.created` is broadcast only once an order reaches `PLACED` (after payment, or immediately for COD). The pending-payment step only emits `booking.updated`. Agency toasts key off `booking.created`.
- Auto-assign: fewest current drops → online first → higher on-time %.
- Yearly domestic quota counts deliveries since 1 April (Indian financial year).
- Delivery ETA is a fake 18-minute trip that falls linearly with route progress.
- Complete-delivery for COD requires the "cash collected" confirmation; wrong OTP is rejected with HTTP 422.
- "Reset demo" regenerates the seed relative to *now* and clears in-flight trips.
- `/demo/simulate payment_failure`: fails the newest `PENDING_PAYMENT` booking if one exists; otherwise arms "next checkout fails".

## B2B pivot (18 Sep 2026) — see PRD_B2B_ADDENDUM.md
- **Days of LPG left** = (spare full + ½ × in-use) ÷ (cylinders per week ÷ 7). Consumption is re-estimated from the last 8 weeks of deliveries at each delivery; the onboarding value is a fallback.
- **Credit:** admin sets status/limit/terms; ordering on credit is blocked when not approved, over limit, or any invoice is overdue. Invoices are raised **on delivery** (due = delivered + term days); payments clear the oldest invoices first.
